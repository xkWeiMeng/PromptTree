## 目標：「開発プロセスのプロンプト」を同じエンジニアリングパイプラインに組み込む

多くのチームが開発フローで大量のプロンプトを使っていますが、よくある課題は依然として存在します：
- 開発中に一時的に書いたプロンプトが最終的にローカルの履歴に埋もれてしまう
- プロジェクトごとにプロンプトを個別管理しており、命名が混乱し、バージョンが不明確
- 本番サービスで使用しているプロンプトがチームドキュメントと一致していない

プロンプトをコードのように管理したいのであれば、**公式 Skills + API キー**を組み合わせて使うことをお勧めします。

## 役割分担：Skills は蓄積を、API キーは配信を担当

- **Skills**：開発フロー内でプロンプトを自動的に抽出、整理、登録（手動のアーカイブ作業を削減）
- **API キー**：アプリケーションやサービスが PromptTree から最新テンプレートを取得（手動同期を削減）

一言でまとめると：
**Skills は「いかに継続的に収集するか」を解決し、API キーは「いかに安定的に使用するか」を解決します。**

## 推奨ワークフロー（すぐに実行可能）

### 第1ステップ：プロジェクト内のプロンプト構造を確立

PromptTree でまず統一ディレクトリを構築します。例えば：
- `プロダクト/要件分析`
- `開発/コード生成`
- `開発/コードレビュー`
- `運営/コンテンツ制作`

各ディレクトリ内でテンプレート化されたプロンプトを管理します（`{{language}}`、`{{module}}`、`{{tone}}`）。

### 第2ステップ：公式 Skills で自動バックアップを有効化

開発フローに公式 Skills を設定し、以下のタイミングで自動的にプロンプトを記録します：
- 重要なプロンプトを新規追加した時
- 既存のプロンプトに構造的な変更を加えた時
- タスク完了後に再利用可能なテンプレートを蓄積する時

これにより、開発中の価値あるプロンプトが「手動でコピーして保存」に依存しなくなります。

### 第3ステップ：アプリケーション側から API キーでプロンプトを取得

ソフトウェアやシステムが API キーを接続した後、2つの取得戦略が使えます：

1. **起動時取得**：サービス起動時に現在の安定バージョンを取得
2. **定期取得**：一定間隔で最新の変更を取得

ビジネス実行時は変数値のみを渡し、テンプレートは PromptTree から取得することで、本番の統一性を確保します。

### 第4ステップ：変更のリリースとロールバック

PromptTree で修正を完了した後：
- 変更説明を記録する（今回の変更がどのシーンに影響するか）
- ステージング環境で先に検証する
- 設定の切り替えで新バージョンに移行する
- 問題発生時は前の安定バージョンに戻す

これにより、プロンプトの更新が「本番テキストの盲目的な変更」ではなくなります。

## シナリオ例：システムが最新の変更を自動取得

「チケット自動返信システム」を例にとります：

1. PromptTree で「返金説明テンプレート」を更新
2. システムが定期タスクで最新のプロンプトを取得
3. 新しいチケットは更新後のテンプレートで自動的に返信を生成
4. 指標に異常があれば、前のバージョンのテンプレートに切り戻し

プロセス全体でコード変更やデプロイは不要で、すべての変更が追跡可能です。

## 実施のアドバイス（よくある落とし穴を回避）

- 統一した命名規則でプロンプトを管理（ビジネスドメイン/シーン/アクション）
- 重要なプロンプトには責任者を設定し、複数人の無秩序な上書きを防止
- 「テンプレートの修正」をリリースフローに組み込み、場当たり的な操作にしない
- PromptTree を唯一のソースとし、下流での長期的なローカルキャッシュのコピーを禁止

## まとめ

Skills と API キーを組み合わせて使うことで得られるのは、「より便利にプロンプトを書ける」ことだけではなく、持続可能なエンジニアリング能力です：
- 開発プロセスでプロンプトを自動バックアップ
- プロジェクト横断でプロンプト資産を統一管理
- システムが最新の変更を自動取得し安定的に運用

最終的に、プロンプトはもはや散在するテクニックではなく、ガバナンス可能で、再利用可能で、進化し続ける生産資産になります。
