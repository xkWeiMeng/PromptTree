## 먼저 결론부터: API 키는 프롬프트를 "수작업 자산"에서 "시스템 자산"으로 변환합니다

웹 페이지에서 프롬프트를 수동으로 복사하기만 한다면, 그것은 개인 메모에 가깝습니다.  
하지만 비즈니스가 이미 '대량 생성, 자동 실행, 크로스 시스템 협업' 단계에 진입했다면, 프롬프트도 프로그래밍 방식의 관리에 편입되어야 합니다.

이것이 API 키의 의미입니다:  
**여러분의 애플리케이션, 스크립트, 워크플로 플랫폼이 PromptTree의 프롬프트 자산을 안전하게 읽고 쓸 수 있게 합니다.**

## API 키가 없을 때 발생하는 문제

많은 팀에서 흔히 보이는 방식은:
- 프롬프트를 코드에 하드코딩함
- 프롬프트를 변경하려면 배포가 필요함
- 서로 다른 서비스가 "거의 동일한" 프롬프트를 각각 관리함
- 문제 발생 시 어떤 버전이 실제 운영 환경에서 동작하는지 추적이 어려움

이는 두 가지 직접적인 비용을 초래합니다:
- **반복 속도 저하**: 사소한 변경에도 전체 배포 프로세스를 거쳐야 합니다
- **일관성 부족**: 실제 운영 동작과 팀의 인식이 종종 불일치합니다

## API 키로 프롬프트를 관리하는 전형적인 방법

권장 프로세스:

1. PromptTree에서 프롬프트를 작성하고 관리합니다(변수, 분류, 버전 반복 지원)
2. 서비스용 API 키를 생성합니다(환경과 용도별로 분리)
3. 서비스 시작 시 프롬프트를 가져오거나, 필요 시 실시간으로 요청합니다
4. 비즈니스 측에서는 변수만 전달하고, 프롬프트 템플릿은 통합 소스에서 제공합니다

이렇게 하면 애플리케이션 레이어는 "비즈니스 파라미터"에, PromptTree는 "템플릿 거버넌스"에 집중할 수 있습니다.

## 이 기능을 개방한 이유

API 키를 개방한 것은 "인터페이스 하나를 더 추가하기 위해서"가 아니라, 프롬프트 관리를 진정으로 엔지니어링 체계에 편입시키기 위해서입니다:

### 1) 자동화 지향

프롬프트는 사람만을 위한 것이 아니라, 시스템도 서비스해야 합니다.  
API를 통해 프롬프트를 CI, 작업 오케스트레이터, 내부 도구 체인에 연결할 수 있습니다.

### 2) 통합 거버넌스 지향

팀에는 하나의 프롬프트 진실의 원천(Single Source of Truth)이 있어야 합니다.  
API 키를 통해 각 시스템이 동일한 소스에서 읽어 들이고, 각자 복사하는 것을 방지합니다.

### 3) 감사 가능성과 롤백 지향

프롬프트 변경이 운영 환경 효과에 영향을 미칠 때, "누가 무엇을 바꿨는지, 언제 바꿨는지, 현재 버전이 무엇인지" 알아야 합니다.  
통합 관리와 버전화 프로세스를 통해 추적과 롤백이 비로소 실행 가능해집니다.

## 모범 사례 권장사항

- 환경별로 키를 분리하세요: 개발 / 스테이징 / 프로덕션 각각 설정
- 서비스별로 키를 분리하세요: 다른 시스템은 독립 자격증명을 사용하여 리스크 범위를 축소
- 키를 리포지토리에 저장하지 마세요: 환경 변수 또는 시크릿 관리 시스템을 통해 주입
- 프롬프트 ID를 비즈니스 설정 레이어에 고정하세요: 코드 내 문자열 상수가 흩어지는 것을 방지

## 요약

API 키로 프롬프트를 관리하는 본질은, 프롬프트를 "개인 생산성 도구"에서 "팀 인프라"로 업그레이드하는 것입니다.  
이 기능을 개방한 이유는, 거버넌스 능력을 희생하지 않으면서 AI 역량을 실제 비즈니스 시스템에 안정적으로 연동할 수 있도록 하기 위해서입니다.
