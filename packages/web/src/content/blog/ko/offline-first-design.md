## 오프라인 우선이란

"오프라인 우선"은 "오프라인에서도 사용 가능"과는 다릅니다. 이는 로컬 저장소가 데이터의 **첫 번째 소스**이며, 클라우드 동기화는 **부가 서비스**임을 의미합니다.

기존 SaaS 애플리케이션은 "온라인 우선"입니다 — 데이터가 클라우드에 저장되고 로컬은 단지 캐시에 불과합니다. 이 모델에서는 네트워크가 없으면 사용할 수 없습니다.

PromptTree는 반대입니다: 데이터를 우선 로컬 데이터베이스(IndexedDB)에 기록한 후, 비동기적으로 클라우드에 동기화합니다. 클라우드 서비스가 다운되더라도 여러분의 앱은 완전히 정상 작동합니다.

## 오프라인 우선을 선택한 이유

### 1. 제로 레이턴시 경험

모든 작업이 로컬 데이터베이스를 직접 읽고 쓰므로, 응답 시간은 밀리초 수준입니다. 네트워크 요청을 기다릴 필요 없이 생성, 편집, 검색이 모두 즉시 완료됩니다.

### 2. 항상 사용 가능

지하철에서 프롬프트 라이브러리를 살펴보고 싶으신가요? 비행기에서 템플릿 두 개를 수정하고 싶으신가요? 전혀 문제없습니다. 개인 생산성 도구에서 "항상 사용 가능"은 기본 요건입니다.

### 3. 데이터 자주권

여러분의 프롬프트는 여러분 자신의 디바이스에 저장됩니다. 설령 언젠가 PromptTree 서비스가 종료되더라도(그러지 않기를 바랍니다), 여러분의 데이터는 브라우저의 IndexedDB에 안전하게 남아 있습니다.

### 4. 가입 없이 사용 가능

오프라인 우선 덕분에 "가입 없이" 사용할 수 있습니다. 새로운 사용자가 PromptTree를 열면, 어떤 양식도 작성하지 않고 바로 사용을 시작할 수 있습니다. 이는 제품의 진입 장벽을 낮춥니다.

## 기술 구현

### 로컬 저장소

웹 버전은 Dexie.js 라이브러리를 사용하여 IndexedDB를 조작합니다. 모든 데이터에는 동기화가 필요한지 여부를 나타내는 `_dirty` 마커가 있습니다.

### 증분 동기화

가입 및 로그인 후, 로컬 변경 사항은 증분 동기화를 통해 클라우드에 업로드됩니다:

1. 데이터 수정 → IndexedDB에 기록, `_dirty = true` 마킹
2. 2초 디바운스 → 모든 dirty 데이터 수집
3. POST `/api/sync` → 변경 사항 업로드, 다른 디바이스의 업데이트 가져오기
4. 로컬 데이터 업데이트 → `_dirty` 마커 해제

### 충돌 해결

여러 디바이스에서 동시에 같은 데이터를 수정할 경우, Last Write Wins 전략을 사용합니다 — `updatedAt` 타임스탬프를 비교하여 가장 최신 버전을 유지합니다.

## 트레이드오프

오프라인 우선에도 비용이 있습니다:

- **데이터 일관성**: 멀티 디바이스 실시간 협업을 완벽하게 보장하기 어렵고, 짧은 불일치 구간이 존재할 수 있습니다
- **저장 공간**: 로컬에 전체 데이터셋을 저장해야 합니다(다만 프롬프트 데이터의 양은 보통 매우 적습니다)
- **아키텍처 복잡도**: 동기화 로직이 순수 온라인 모드보다 복잡합니다

PromptTree와 같은 개인 생산성 도구에서는 이러한 트레이드오프가 충분히 가치 있다고 판단합니다. 사용자가 얻는 것은 더 빠르고, 더 안정적이며, 더 통제감 있는 사용 경험입니다.

## 마치며

오프라인 우선은 기술적 과시가 아닌, 제품 사용 시나리오에 대한 깊은 고려입니다. 네트워크에 점점 더 의존하는 세상에서, 도구가 네트워크에 의존하지 않게 만드는 것은 오히려 경쟁 우위가 됩니다.
