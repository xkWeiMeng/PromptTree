## 先说结论：API Key 让 Prompt 从“手工资产”变成“系统资产”

如果你只在网页里手动复制 Prompt，那它更像个人笔记。  
但当你的业务已经进入「批量生成、自动执行、跨系统协同」阶段，Prompt 必须进入程序化管理。

这就是 API Key 的意义：  
**让你的应用、脚本、工作流平台，可以安全地读写 PromptTree 中的 Prompt 资产。**

## 没有 API Key 时会发生什么

在很多团队里，常见做法是：
- 把 Prompt 硬编码在代码里
- 改 Prompt 需要发版
- 不同服务各自维护一份“几乎相同”的 Prompt
- 出问题时很难追踪到底哪个版本在线上生效

这会带来两个直接成本：
- **迭代慢**：小改动也要走完整发布流程
- **一致性差**：线上行为和团队认知常常不一致

## 用 API Key 管理 Prompt 的典型方式

一个推荐流程：

1. 在 PromptTree 编写与维护 Prompt（支持变量、分类、版本迭代）
2. 为你的服务生成 API Key（按环境和用途分开）
3. 服务启动时拉取 Prompt，或按需实时获取
4. 在业务侧仅传变量，Prompt 模板由统一源提供

这样做后，应用层关注“业务参数”，PromptTree 负责“模板治理”。

## 我们为什么要开放这个功能

我们开放 API Key，不是为了“多一个接口”，而是为了让 Prompt 管理真正进入工程体系：

### 1) 面向自动化

Prompt 不应只服务人，也应服务系统。  
API 能把 Prompt 接进 CI、任务编排器、内部工具链。

### 2) 面向统一治理

一个团队应该有一个 Prompt 真相源（single source of truth）。  
API Key 让各系统都从同一个源读取，而不是各自复制。

### 3) 面向可审计与可回滚

当 Prompt 变更影响线上效果时，你需要知道“谁改了什么、何时改的、当前版本是什么”。  
通过统一管理与版本化流程，回溯和回滚才可执行。

## 最佳实践建议

- 按环境拆分 Key：开发 / 预发 / 生产分别配置
- 按服务拆分 Key：不同系统使用独立凭证，降低风险面
- 不要把 Key 写入仓库：通过环境变量或密钥管理系统注入
- 把 Prompt ID 固定在业务配置层：避免代码内散落字符串常量

## 总结

API Key 管理 Prompt 的本质，是把 Prompt 从“个人效率工具”升级为“团队基础设施”。  
开放这个能力，是为了让你可以在不牺牲治理能力的前提下，把 AI 能力稳定接入真实业务系统。
