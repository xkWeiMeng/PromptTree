## 先說結論：API Key 讓 Prompt 從「手工資產」變成「系統資產」

如果你只在網頁裡手動複製 Prompt，那它更像個人筆記。  
但當你的業務已經進入「批量產生、自動執行、跨系統協同」階段，Prompt 必須進入程式化管理。

這就是 API Key 的意義：  
**讓你的應用程式、腳本、工作流程平台，可以安全地讀寫 PromptTree 中的 Prompt 資產。**

## 沒有 API Key 時會發生什麼

在很多團隊裡，常見做法是：
- 把 Prompt 寫死在程式碼裡
- 改 Prompt 需要發版
- 不同服務各自維護一份「幾乎相同」的 Prompt
- 出問題時很難追蹤到底哪個版本在線上生效

這會帶來兩個直接成本：
- **迭代慢**：小改動也要走完整發布流程
- **一致性差**：線上行為和團隊認知常常不一致

## 用 API Key 管理 Prompt 的典型方式

一個推薦流程：

1. 在 PromptTree 編寫與維護 Prompt（支援變數、分類、版本迭代）
2. 為你的服務產生 API Key（按環境和用途分開）
3. 服務啟動時拉取 Prompt，或按需即時取得
4. 在業務側僅傳變數，Prompt 範本由統一源提供

這樣做後，應用層關注「業務參數」，PromptTree 負責「範本治理」。

## 我們為什麼要開放這個功能

我們開放 API Key，不是為了「多一個介面」，而是為了讓 Prompt 管理真正進入工程體系：

### 1) 面向自動化

Prompt 不應只服務人，也應服務系統。  
API 能把 Prompt 接進 CI、任務編排器、內部工具鏈。

### 2) 面向統一治理

一個團隊應該有一個 Prompt 唯一真相源（single source of truth）。  
API Key 讓各系統都從同一個源讀取，而不是各自複製。

### 3) 面向可稽核與可回滾

當 Prompt 變更影響線上效果時，你需要知道「誰改了什麼、何時改的、目前版本是什麼」。  
透過統一管理與版本化流程，回溯和回滾才可執行。

## 最佳實踐建議

- 按環境拆分 Key：開發 / 預發 / 正式環境分別設定
- 按服務拆分 Key：不同系統使用獨立憑證，降低風險面
- 不要把 Key 寫入儲存庫：透過環境變數或金鑰管理系統注入
- 把 Prompt ID 固定在業務設定層：避免程式碼內散落字串常數

## 總結

API Key 管理 Prompt 的本質，是把 Prompt 從「個人效率工具」升級為「團隊基礎設施」。  
開放這個能力，是為了讓你可以在不犧牲治理能力的前提下，把 AI 能力穩定接入真實業務系統。
